# Проверка извлечения позиций, количества и цены — 25.10.2026

## Цель

Для каждой позиции чека вернуть название, количество, цену за единицу и сумму строки. Сравнивались только на validation; test не использовался для подбора.

## Эксперименты

### Donut с четырьмя полями

Дообучили `naver-clova-ix/donut-base` на отдельном наборе с полями `name`, `quantity`, `price`, `sum`: 542 чека train и 114 validation (1 901 и 379 позиций). Использовали русские символы с инициализацией их embedding через транслитерацию. Лучший checkpoint сохранён отдельно в `ml/models/donut-receipts/full_fields_translit_2026-10-25/best/`.

| Поле / метрика | Validation |
|---|---:|
| Валидный JSON | 89,6% чеков |
| Название, exact-match F1 | 3,9% |
| Количество, exact-match F1 | 63,8% |
| Цена за единицу, exact-match F1 | 49,1% |
| Сумма строки, exact-match F1 | 47,8% |
| CER названий | 0,873 |
| Полностью совпали все пары «название + сумма» в чеке* | 4,3% |
| Точная строка «название + количество + цена + сумма», F1 | 3,3% |
| Чеки, где точно совпали все строки из четырёх полей | 4,3% |

* Метрика полного чека в исходном оценщике сравнивает пары «название + сумма». Для полного кортежа из четырёх полей отдельно посчитаны 10 точных строк из 379 целей (F1 3,3%) и 5 из 115 чеков с точным совпадением всех строк.

Это не пригодно для автоматического принятия результата: названия почти всегда ошибочны, а JSON примерно в одном случае из десяти требует исправления. Checkpoint не заменяет основную модель.

### PaddleOCR и каталог позиций

Запустили готовую мультиязычную PaddleOCR на всех 115 чеках validation. На первых 24 чеках отдельно сравнили стандартный размер детектора (736 px) с увеличенным (1280 px). Увеличение не улучшило распознавание названий; доля строк с высокой похожестью немного снизилась. Числа попадали чаще, но значения остались недостаточными.

Дополнительно классифицировали OCR-строки по каталогу из 1 037 уникальных названий train. Название кандидата выбиралось по OCR тексту; validation разметка использовалась только для оценки. Результат при пороге похожести 0,65: precision 44,8%, recall 12,4% (47 точных названий из 379). При более мягком пороге 0,45 recall 18,7%, precision 12,1%. Даже когда каталог точно угадал строку, quantity нашлось в OCR в 43,7% случаев, price и sum — в 74,6%. Для всех позиций этот подход не годится.

Сырые распознанные блоки, диагностика и параметры находятся в `ml/reports/paddleocr_validation*.jsonl`, `ml/reports/paddleocr_*analysis.json`; скрипты — `ml/scripts/run_paddle_ocr.py`, `ml/scripts/analyze_paddle_ocr.py` и `ml/scripts/evaluate_paddle_catalog.py`.

### Полный fine-tuning визуального энкодера

Провели пилот дообучения всего энкодера Donut на MPS, начиная с полного четырехполевого checkpoint. Начальная validation loss была 0,735. На одном шаге оптимизации процесс не продвинулся за несколько минут, поэтому эксперимент остановили до обновления весов. Сохранённый основной checkpoint не затронут. Реализованный флаг `--train-encoder` позволяет повторить эксперимент на более мощном устройстве; этот запуск улучшением не считается.

## Вывод

**Нет, названия, количество и цена пока не извлекаются с минимально приемлемой надёжностью.** Donut лучше справляется с количеством, но exact-match F1 названий — 3,9%; OCR-кандидат с каталогом не достигает даже 45% recall точных названий при пороге с умеренной точностью. Текущие веса нельзя подключать в приложение как готовую модель.

Для сравнения на 02.11 предлагается принять порог готовности: валидный JSON не ниже 98%, exact-match F1 названий не ниже 70%, количества/цены/суммы — не ниже 90% каждое, метрика полного совпадения строки (название + количество + цена + сумма) не ниже 70% на validation. При достижении порога зафиксировать кандидата и один раз измерить его на test. Если порог не достигнут, честно перенести готовность и не выдавать экспериментальный checkpoint за завершённую модель.
